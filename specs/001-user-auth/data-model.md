## Domain Entities

### User Account

**Purpose**: Represents a user registered in the system

**Fields**:
- `id: string` (UUID v4) - Unique identifier, auto-generated by backend
- `username: string` - 3-20 alphanumeric characters + underscore, unique constraint
- `password: string` - 6-50 characters, bcrypt hashed (backend responsibility, never exposed to frontend)
- `createdAt: string` (ISO 8601) - Account creation timestamp

**Constraints**:
- Username is unique across all accounts
- Username matches regex: `/^[a-zA-Z0-9_]{3,20}$/`
- Password is never transmitted or stored in plain text on frontend
- Password is hashed with bcrypt (salt rounds: 10) on backend
- User data is only exposed after successful authentication

**Relationships**:
- User has one active Session (at a time)
- User can have multiple past Sessions (if tracking is implemented)

---

### User Session

**Purpose**: Represents an authenticated session for a user

**Fields**:
- `id: string` - Session identifier (managed by express-session via cookie)
- `userId: string` - Foreign key to User
- `username: string` - Cached username for quick access without fetching user
- `createdAt: number` - Session creation timestamp (server time)
- `expiresAt: number` - Session expiration timestamp (7 days from creation)
- `isValid: boolean` - Whether session is still active

**Lifetime**:
- Created automatically upon successful login
- Stored in HTTP-only cookie named `connect.sid`
- Expires after 7 days of creation
- Cleared on explicit logout

**Access**:
- Not directly accessible to JavaScript (HTTP-only flag)
- Automatically sent by browser in all requests
- Backend validates on each protected endpoint

**Constraints**:
- Session must be HttpOnly (not accessible to JavaScript)
- Session must be Secure in production (HTTPS only)
- Session expiration is server-time based (prevents client manipulation)

**Relationships**:
- Session belongs to one User
- One active session per user (newer login invalidates previous session if implemented)

### Authentication Request

**Purpose**: Data structure for login/registration submissions

#### Registration Request
```typescript
interface RegisterRequest {
  username: string;        // 3-20 alphanumeric + underscore
  password: string;        // 6-50 characters
}
```

**Validation** (client-side, pre-submission):
- Username: Match `/^[a-zA-Z0-9_]{3,20}$/`
- Password: Length 6-50 characters
- Both fields required (not empty)

**Validation** (server-side, authoritative):
- Same format validation
- Check username not already in use
- Enforce constraints via database

#### Login Request
```typescript
interface LoginRequest {
  username: string;        // User-provided value
  password: string;        // User-provided value
}
```

**Validation** (client-side):
- Both fields required (not empty)
- Show validation errors in real-time

**Validation** (server-side):
- Find user by username
- Verify password against stored hash
- Generic error if either fails (security)

### Authentication Response

**Purpose**: Data returned by authentication endpoints

#### Success Response
```typescript
interface AuthSuccessResponse {
  success: true;
  message: string;         // e.g., "登录成功", "注册成功"
  data: {
    id: string;           // User ID (UUID)
    username: string;     // Confirmed username
  };
}
```

**Additional side effects**:
- Backend sets `Set-Cookie` header with session cookie
- Session cookie contains encrypted session ID
- Browser automatically stores and sends cookie with future requests

#### Error Response
```typescript
interface AuthErrorResponse {
  success: false;
  message: string;        // User-friendly error message
  error: ErrorCode;       // Machine-readable error code
}

type ErrorCode = 
  | 'MISSING_FIELDS'       // 400: Required fields missing
  | 'INVALID_USERNAME'     // 400: Username format invalid
  | 'INVALID_PASSWORD'     // 400: Password format invalid
  | 'MISSING_CREDENTIALS'  // 400: Login fields missing
  | 'INVALID_CREDENTIALS'  // 401: Wrong username/password
  | 'USERNAME_EXISTS'      // 409: Username already registered
  | 'INTERNAL_ERROR';      // 500: Server error
```

**Error Mapping** (frontend responsibility):
- `MISSING_FIELDS` → "Username and password are required"
- `INVALID_USERNAME` → "Username must be 3-20 characters, letters/numbers/_only"
- `INVALID_PASSWORD` → "Password must be 6-50 characters"
- `MISSING_CREDENTIALS` → "Please enter username and password"
- `INVALID_CREDENTIALS` → "Invalid username or password"
- `USERNAME_EXISTS` → "Username already taken. Try another or login"
- `INTERNAL_ERROR` → "Server error. Please try again later"

## Form Data State

### Registration Form State
```typescript
interface RegisterFormState {
  username: string;
  password: string;
  errors: {
    username?: string;
    password?: string;
    submit?: string;
  };
  isLoading: boolean;
  isSubmitted: boolean;
}
```

**Lifecycle**:
1. User enters username/password
2. Validation runs on blur (show errors)
3. User clicks submit
4. Client validates again
5. If valid, set `isLoading = true`, disable form
6. POST to `/auth/register`
7. On success: Show success message, redirect to login or dashboard
8. On error: Set `errors.submit`, show error message, allow retry

### Login Form State
```typescript
interface LoginFormState {
  username: string;
  password: string;
  errors: {
    submit?: string;  // Generic error (no field-specific errors)
  };
  isLoading: boolean;
  isSubmitted: boolean;
}
```

**Lifecycle**:
1. User enters username/password
2. No real-time validation (both required only)
3. User clicks submit
4. If empty, show error
5. If both present, set `isLoading = true`
6. POST to `/auth/login`
7. On success: Store user info if needed, set session via cookie, redirect to dashboard
8. On error: Set `errors.submit`, show error, allow retry
9. On 401: Redirect to login page after showing session expired message

## Validation Rules

### Username Validation

**Format Rule**:
- Pattern: `/^[a-zA-Z0-9_]{3,20}$/`
- Length: 3-20 characters
- Allowed characters: a-z, A-Z, 0-9, underscore (_)
- No spaces, special characters, or Unicode

**Error Messages**:
- Too short: "Username must be at least 3 characters"
- Too long: "Username must be at most 20 characters"
- Invalid characters: "Username can only contain letters, numbers, and underscore"
- Combined: "Username must be 3-20 characters with letters, numbers, and underscore only"

**Timing**:
- Client validation: Debounced 300ms on input change
- Show error: On blur or after submission attempt
- Server validation: Always, before accepting registration

### Password Validation

**Format Rule**:
- Length: 6-50 characters
- Allowed characters: All characters (no restrictions)

**Error Messages**:
- Too short: "Password must be at least 6 characters"
- Too long: "Password must be at most 50 characters"
- Combined: "Password must be 6-50 characters"

**Timing**:
- Client validation: On blur or during submission
- No real-time validation as user types (password field convention)
- Server validation: Always, before accepting submission

**Security**:
- Password never logged or displayed
- Password never stored in frontend state (clear after submit)
- Password never sent to API twice (no confirm field)
- Password sent only over HTTPS in production

## State Transitions

### Registration Flow
```
Start
  ↓
User enters username/password
  ↓
User clicks "Sign Up"
  ├─ Client validation fails → Show field errors → Allow retry
  └─ Client validation passes
    ↓
  Show loading state, disable form
    ↓
  POST /auth/register
    ├─ Success → Clear form, show "Registration successful" → Redirect to login/dashboard
    ├─ 409 (USERNAME_EXISTS) → Show "Username taken" → Allow retry
    ├─ 400 (validation) → Show specific error → Allow retry
    ├─ 500 (server error) → Show "Server error" → Allow retry
    └─ Network error → Show "Connection error" → Allow retry
```

### Login Flow
```
Start
  ↓
User enters username/password
  ↓
User clicks "Sign In"
  ├─ Validation fails (empty field) → Show error → Allow retry
  └─ Validation passes
    ↓
  Show loading state, disable form
    ↓
  POST /auth/login
    ├─ 200 (success) → Store session (cookie) → Redirect to dashboard
    ├─ 401 (INVALID_CREDENTIALS) → Show "Invalid username or password" → Allow retry
    ├─ 400 (validation) → Show specific error → Allow retry
    ├─ 500 (server error) → Show "Server error" → Allow retry
    └─ Network error → Show "Connection error" → Allow retry
```
